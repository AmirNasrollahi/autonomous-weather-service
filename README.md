# Autonomous Weather Service (سیستم سرویس آب‌وهوا برای خودروهای خودران)

سرویس مقاوم و مستقل دریافت و کش اطلاعات آب‌وهوای مسیر خودرو با استفاده از **.NET 8 LTS**، طراحی‌شده بر اساس اصل **KISS**، با قابلیت پایداری و کارکرد مداوم **۲۰ ساله** بدون نیاز به مداخله انسانی، اینترنت پایدار، یا به‌روزرسانی نرم‌افزاری.

---

## ۱. نمای کلی سیستم و اهداف طراحی

نرم‌افزار خودروهای خودران پس از استقرار نهایی به دلیل ملاحظات امنیتی و ایزولاسیون سخت‌افزاری، امکان به‌روزرسانی، تغییر کانفیگ دستی یا مداخله انسانی را نخواهد داشت. این سرویس به عنوان دروازه تأمین داده‌های آب‌وهوا برای ماژول‌های حیاتی خودرو (موتور، سیستم تهویه، مدیریت انرژی و مسیریابی) عمل می‌کند و ویژگی‌های زیر را تضمین می‌نماید:

- **ذخیره و تحویل داده بدون تغییر (Raw JSON):** داده‌های هواشناسی دریافت شده از Open-Meteo بدون هیچ‌گونه دیسریالایز یا تبدیل ساختاری در دیتابیس محلی ذخیره شده و به همان شکل خام به کلاینت تحویل داده می‌شوند (مصون از تغییرات فرمت داده در گذر ۲۰ سال).
- **تحمل خطای ارتباطی (Fault Tolerance):** در صورت افت کیفیت یا قطعی ارتباط بی‌سیم خودرو (تا ۳۰٪ خطای تخمینی)، داده‌های معتبر قبلی فوراً از دیتابیس محلی فراخوانی و تحویل می‌شوند.
- **رعایت سقف مهلت پاسخ (Strict Deadline):** حداکثر زمان انتظار کلاینت ۳ ثانیه است؛ سرویس دارای مهلت داخلی است تا پاسخ قطعی در هر شرایطی درون مهلت مجاز تحویل شود.
- **قرارداد پایدار ۳ حالته (Three-State Predictable Contract):** کلاینت‌های خودرویی هرگز با خطای ۵۰۰ یا خروجی‌های غیرمنتظره روبرو نمی‌شوند؛ پاسخ همواره HTTP 200 با بدنه معتبر JSON است (داده تازه، داده فال‌بک، یا مقدار `null`).

## ۲. تصمیمات کلیدی معماری و مهندسی

### ۲.۱. جلوگیری از رشد بی‌نهایت دیتابیس با SQLite Atomic Upsert
در صورتی که هر دقیقه یک رکورد در دیتابیس درج شود، طی ۲۰ سال بیش از ۱۰ میلیون رکورد (~۴۰ گیگابایت) روی حافظه فلش خودرو ایجاد می‌شود.
- **راهکار:** یک ایندکس یکتا (Unique Index) روی مختصات `(Latitude, Longitude)` تعریف شده و ذخیره‌سازی از طریق دستور اتمیک `INSERT ... ON CONFLICT DO UPDATE` انجام می‌شود. بدین ترتیب برای هر موقعیت مکانی تنها **آخرین داده معتبر** نگهداری شده و حجم کل دیتابیس حتی پس از ۲۰ سال در حد چند کیلوبایت یا مگابایت باقی می‌ماند.

### ۲.۲. جداسازی ذخیره‌سازی از مسیر پاسخ (Zero-Latency Save)
در سناریوی موفق، داده دریافت شده از API خارجی بلافاصله به کلاینت تحویل داده می‌شود و عملیات ذخیره‌سازی به صورت مستقل و Non-blocking در پس‌زمینه انجام می‌پذیرد. در نتیجه کلاینت خودرو معطل دیسک یا قفل‌های احتمالی دیتابیس نمی‌شود و پاسخ در کمترین زمان ممکن (زیر ۱۰۰ میلی‌ثانیه) تحویل می‌گردد.

### ۲.۳. الگوی Single-Flight با ایزولاسیون کامل Cancellation
هنگام ارسال هم‌زمان چندین استعلام برای یک مختصات (مثلاً فراخوانی هم‌زمان سیستم تهویه و موتور):
- از `Lazy<Task<string?>>` با مد `ExecutionAndPublication` استفاده شده تا تحت هیچ شرایطی بیش از یک درخواست خارجی ارسال نشود.
- مکانیزم پاک‌سازی مشروط (`TryRemove` با مقدار تطبیقی) از Race Condition پاک‌شدن ناخواسته تسک‌های هم‌زمان جلوگیری می‌کند.
- لغو درخواست (Cancel) توسط یک کلاینت، فقط انتظار همان کلاینت را متوقف می‌کند و تسک در حال اجرای مشترک برای سایر درخواست‌دهنده‌ها بدون وقفه ادامه می‌یابد.

### ۲.۴. محافظت از حافظه فلش خودرو در برابر فرسودگی (Flash Wear Mitigation)
نوشتن مداوم لاگ در هر دقیقه طی ۲۰ سال سلول‌های حافظه NAND فلش خودرو را مستهلک می‌کند.
- لاگ‌های پرحجم Information فریم‌ورک EF Core و ASP.NET Core به سطح `Warning` محدود شدند.
- لاگ فایل Serilog روی سطح `Warning` و حداکثر ۵ فایل ۱۰ مگابایتی محدود شده است تا لاگ‌ها صرفاً در شرایط خطا یا هشدار ثبت شوند.

### ۲.۵. مدیریت زمان و رفع مسدود شدن SQLite
- گزینه `Cache=Shared` به دلیل ایجاد قفل‌های سطح جدول و عدم سازگاری با حالت WAL حذف گردید.
- پارامتر `Default Timeout=1` در Connection String و `CommandTimeout(1)` در EF Core تنظیم شد تا در صورت قفل بودن دیتابیس، هیچ ریسمانی بیشتر از ۱ ثانیه معطل نماند.

### ۲.۶. خودترمیمی هوشمند در Startup (Self-Healing Storage)
- در صورت وقوع خرابی در فایل دیتابیس (مثلاً ناشی از قطع برق ناگهانی خودرو)، فایل خراب به `weather.db.corrupt` تغییر نام می‌یابد (جهت امکان بررسی‌های عیب‌یابی در تعمیرگاه خودرو) و یک دیتابیس تازه در حالت پایدار `WAL` ساخته می‌شود تا سرویس هرگز در زمان بالا آمدن Crash نکند.

## ۴. نحوه ساخت و اجرای پروژه

### پیشنیازها:
- [.NET 8.0 SDK](https://dotnet.microsoft.com/download/dotnet/8.0)

### ۱. بیلد پروژه:
```bash
dotnet build WeatherService.sln
```

### ۲. اجرای تست‌های خودکار (شامل ۲۲ تست جامع):
```bash
dotnet test
```

### ۳. اجرای سرویس:
```bash
dotnet run --project src/WeatherService.Api/WeatherService.Api.csproj
```

سرویس به صورت پیش‌فرض روی آدرس `http://localhost:5245` اجرا می‌شود.

### ۴. فراخوانی Endpoint:
- **با مختصات پیش‌فرض تسک (52.52, 13.41):**
  ```bash
  curl -i http://localhost:5245/api/weather
  ```
- **با مختصات سفارشی در مسیر خودرو:**
  ```bash
  curl -i "http://localhost:5245/api/weather?latitude=35.6892&longitude=51.3890"
  ```
